## 주요 변경

- 마이그레이션 `20261025151218_alimtalk_template_ownership_lifecycle.sql`: 서버 전용 소유권 레지스트리, 불변 분류·선택 검사 트리거, 탈퇴 중지 트리거, 활성 코드 뷰, 공급자 캐시, 임대 잠금이 있는 정리 원장/RPC. 이전 작업의 `20261025151212_alimtalk_approval_background_sync.sql` 이후 적용한다.
- 관리자 공용 지정 전 검사, 매장별 선택 조회 검사, 기본/전용 문구의 실제 발송 해석 검사, `sendAlimtalkMessage`의 최종 소유권 검사를 추가했다. 발송 함수는 메타데이터에서 매장 ID를 추정하지 않고 정본 발송 요청의 명시적 `shopId`를 사용한다.
- `shop_alimtalk_active_codes`는 심사 중, 현재 선택, 기존 current 표식, 오너 선택을 기다리는 최신 승인본을 포함한다. 과거 탈퇴·초안·선택되지 않은 과거 승인 이력을 매번 공급자에서 읽지 않는다.
- 릴레이의 코드 지정 조회는 전체 목록 API를 호출하지 않는다. 코드 요청 최대 100개, 전체 동시 상세 조회 최대 6개, 대기 중 고유 코드 최대 1,024개, 메모리 캐시 최대 5,000개다. 공급자가 다른 코드를 반환하면 본문을 채택하지 않는다. 전체 목록 발견은 명시적인 관리자 조회로 분리했다.
- DB 캐시 유효 기간은 승인 상태 5분, 그 외 1분이다. 만료되지 않은 코드에는 공급자 조회를 다시 하지 않는다. 늦게 도착한 과거 응답은 새 캐시를 덮어쓰지 못한다. 탈퇴 후 캐시 재등록도 DB가 거부한다.
- `/api/cron/alimtalk-template-cleanup`은 회당 최대 20개, 동시 4개로 처리한다. 실패 결과는 즉시 재전송하지 않고 이후 신선한 상태 조회로 재확인한다. 6회 후에도 불확실하면 `manual_review`로 남긴다. `/api/admin/alimtalk/template-cleanup`은 관리자에게 상태별 건수와 확인 대상 최대 100개를 제공한다. 고객에게 메시지를 보내는 작업은 포함하지 않는다.

## 검증

- 집중 검사 **74건 통과**: 웹 업무 흐름 39, 영속 캐시 5, 정리 작업·권한 5, 릴레이 25. 기존 일반 오너 격리 검사뿐 아니라 관리자 오지정, 잘못 저장된 공용 연결의 발송 차단, 탈퇴 코드 재지정, 공급자의 코드 불일치까지 확인했다.
- 실제 PostgreSQL 18의 별도 임시 DB에 원본 관련 마이그레이션들과 신규 마이그레이션을 적용했다. **탈퇴 코드 100,000개**를 넣은 트랜잭션에서 활성 코드 선별, 공용 전환 금지, 교차 매장 선택 금지, 불변 분류, 탈퇴 시 본문·연결 삭제, 재캐시 금지, 정리 작업 중복 실행 금지, service_role 실제 실행 및 공개 역할 권한 차단을 확인했다. 검사 데이터는 롤백했다.
- 웹 정규 사전 검사 **192건 + 15건 통과**, 웹 운영용 빌드·TypeScript 통과. 신규 관리자 상태 조회·정리 cron 경로가 빌드에 포함됐다.
- 릴레이 빌드·타입 검사, 오너 인증 경계 검사, diff 공백 검사 통과.

## 운영과 공급자 경계

- **커밋·운영 DB 적용·배포·실제 쏘다 템플릿 중지·고객 발송은 실행하지 않았다.** 개발·모의 공급자·로컬 DB의 검증 결과이며 실제 공급자의 10만 건 부하나 계정 한도를 입증한 결과가 아니다.
- 쏘다 공식 문서는 승인 문구의 중지와 심사 요청 취소를 제공하지만, 삭제는 대기(R)·등록(REG)/반려(REJ) 상태로 제한한다. 이번 자동 작업은 확인 가능한 중지/검수 취소까지만 수행한다. `review_cancelled`를 삭제 완료로 표시하지 않는다. 승인 문구의 실제 삭제·보관 기간·계정 quota 회수는 공급자 정책 확인 및 별도 처리가 필요하다. [쏘다 공식 API 안내](https://ssodaa.com/service/api/kakaoapi)
- 등록 한도와 API 호출 한도에 대한 문의는 외부로 발송하지 않았다. 확인 질문은 “동일 계정·발신프로필의 템플릿 총량/활성량 한도, 중지·탈퇴 문구의 quota 포함 여부, 심사·상세 조회 호출 한도, 승인 문구 삭제 절차”다.
- 새 작업을 시작하는 시점의 매장 격리를 검사하며 이미 공급자에게 넘어간 요청을 소급 취소할 수는 없다. 검사한 경로의 차단 근거를 제공하며 전체 시스템의 혼용 확률이 수학적으로 0이라는 주장은 하지 않는다.

## 운영 반영 순서

1. 이전 승인 동기화 마이그레이션과 신규 소유권·생명주기 마이그레이션을 순서대로 적용하고, 레지스트리·격리 트리거·서버 전용 권한을 읽어 확인한다.
2. 코드 지정 직접 조회와 정리 API가 포함된 릴레이를 반영한다.
3. 웹을 반영하고 기존 `CRON_SECRET`으로 승인 동기화·정리 작업 및 관리자 상태 조회 결과를 확인한다.
4. 지정된 시험 매장에서 실제 심사→오너 적용→테스트 번호 수신을 별도로 검증한다. 신규 실발송이나 기존 템플릿 삭제를 검사 목적으로 자동 실행하지 않는다.
