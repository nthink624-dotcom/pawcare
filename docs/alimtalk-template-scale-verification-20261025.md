## 추가 점검: 전체 경로 격리와 탈퇴 누적 규모

아래 표의 성공은 명시된 검사 범위의 결과이며, 전체 경로에서 매장 혼용 가능성이 0이라는 보장은 아니다. 후속 점검에서 다음 보완 사항을 확인했다.

- **관리자 공용 지정 경로의 소유권 검사 누락을 모의 재현했다.** A 매장 전용 요청으로 저장된 코드 D를 관리자 `template-mapping` PUT이 공용 문구로 지정하면, 선택 설정이 없는 B 매장의 실제 문안 해석기가 D를 공용 기본 문구로 반환했다. 일반 오너 API는 이를 직접 공용 지정할 권한이 없지만, 관리자의 지정 실수를 서버와 DB에서 차단하는 보완이 필요하다. 재현은 가상 저장소·공급자 응답으로 수행했으며 실제 발송은 하지 않았다.
- 탈퇴 최종 처리 SQL은 매장을 삭제하며 요청·선택·승인 알림은 매장 FK를 통해 삭제된다. 쏘다의 템플릿 중지·삭제와 연결된 정리 절차는 확인되지 않았다. 따라서 공급자에는 이전 템플릿이 누적될 수 있고, 우리 DB에서 원래 전용 문구였다는 연결도 사라진다. 내용이나 고객 정보를 불필요하게 보관하지 않으면서 코드의 전용/공용 분류와 사용 중지 여부를 유지할 설계가 필요하다.
- 목록 페이징 함수는 추가 모의 검사에서 **50,000개/500페이지**, **100,000개/1,000페이지**의 마지막 항목까지 반환했다. 이는 목록 완전성 검사이며 실제 공급자 처리량·서버 메모리·응답 시간 검사가 아니다.
- 현재 릴레이의 코드 필터는 전체 공급자 목록과 상세 카탈로그를 만든 다음 응답을 줄인다. 그러므로 DB에서 필요한 코드만 전달하더라도 공급자 전체 조회 비용은 줄지 않는다. 캐시가 없는 100,000개 목록은 약 1,000회 목록 호출과 최대 약 100,000회 상세 호출을 요구한다.
- 누적 수만~수십만 건을 운영하려면 활성 매장의 사용 중·심사 중 코드만 동기화하고, 상세를 코드별로 조회·저장하며, 변경된 코드만 갱신해야 한다. 탈퇴 시 즉시 사용을 차단하고 별도 정리 작업으로 공급자 상태와 대조해야 한다. 기존 계정에서 실제 등록 한도와 API 한도를 확인하기 전에는 수만 건 운영 가능으로 확정하지 않는다.

## 구현 내용

- 릴레이: `totalPage`/`totalCount`에 따른 전체 페이지 조회, 중복·불완전 응답 오류 처리, 60초 공유 캐시와 동시 갱신 합치기, 상세 조회 동시 실행 최대 6개, 상세 5분 캐시 및 목록의 변경 시각·상태 변화 시 무효화. 한 템플릿의 상세 조회 실패는 해당 코드만 사용 불가로 만들고 다른 매장은 계속 조회한다.
- 오너 조회: 공급자에 존재한다는 이유만으로 공용 문구로 취급하지 않는다. 해당 매장의 제출 원문과 일치하는 문구 또는 명시적으로 등록된 플랫폼 별칭 연결만 후보로 허용한다. 필요한 코드만 릴레이 응답에 포함한다.
- 승인 알림: 기존 플랫폼 승인 상태는 최초 기준선으로 저장하되, 오너가 제출해 이미 승인된 문구는 첫 동기화에서도 안내한다. 읽음 여부와 실제 발송 문구 선택은 독립적이다. 취소·삭제·원문 불일치는 최신 관찰 상태에서 제외하고 과거 알림 이력은 보존한다.
- 작업 실행: 서버 전용 `alimtalk_approval_job` 테이블과 RPC로 실행 잠금과 다음 매장 위치를 저장한다. 완료한 매장 페이지까지만 진행 위치를 확정하므로 실패한 페이지는 다음 실행에서 다시 처리한다. 고객 메시지를 보내는 작업은 포함하지 않는다.
- 상태 표시와 미리보기 UI는 기존 화면을 유지했다. 기존 동의서·예약·템플릿 편집기 수정 작업도 보존했다.

## 운영 적용 및 미검증 범위

- 새 마이그레이션: `supabase/migrations/20261025151212_alimtalk_approval_background_sync.sql`. 운영 적용 후 서버 전용 작업 테이블·권한·함수를 확인해야 한다.
- 운영 반영에는 릴레이 코드와 웹 코드 배포가 모두 필요하다. 웹 cron은 기존 `CRON_SECRET` 인증을 사용한다. 배포 후 실제 작업 실행과 저장 상태를 읽어서 확인해야 한다.
- 1만 개 검사는 공급자 응답을 모의한 기능 검사다. 실제 쏘다 계정에서 1만 개를 등록하거나 실부하를 발생시킨 검사가 아니다. 계정·발신프로필당 등록 한도와 API 호출 한도는 별도 확인이 필요하다.
- 최초 대량 상세 조회, 쏘다 응답 지연, 캐시와 이어서 처리하는 작업의 영향으로 5분 cron 주기는 승인 안내까지 5분 이내를 보장하는 SLA가 아니다. 실패한 매장 페이지는 진행 위치를 보존하며, 반복 실패 시 운영 점검이 필요하다.
- 실제 오너 문안의 심사 승인, 실제 로그인 화면에서의 조작, 지정한 고객 테스트 번호의 최종 수신은 이번 검사에서 확인하지 않았다. 실제 수신까지 성공했다고 보고하지 않는다.
- 예약금·동의서의 필수 본문·버튼·자동 입력 변수 계약은 유지한다. 모든 종류의 문안을 무제한으로 자유 변경하는 기능은 이번 범위에 포함되지 않는다.
