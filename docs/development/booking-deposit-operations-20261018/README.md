# 예약금 운영 반영 준비 (미활성)

이 폴더는 검토용이다. `cron-config.draft.json`은 자동 배포에 포함되지 않는다. 실제 `vercel.json`, 운영 DB, 외부 릴레이 설정, 요금제는 변경하지 않았다.

## 지속 실행 경로

제안 실행 위치는 PC 웹 운영 Vercel 프로젝트 `petmanager` (`prj_v3zjDSALc0VTY3yLRaNO5Il43uwO`)의 Cron Jobs다. 로컬 연결 파일은 `apps/web/.vercel/project.json`이다. 현재 관리 API의 프로젝트 `rootDirectory` 응답은 null이므로, 활성화 전 실제 배포 산출물에 **웹의** `/api/cron/booking-deposit-expiry`가 포함되는지 확인해야 한다. 모바일용 루트 설정에 초안을 그대로 덮어쓰지 않는다.

관리 API에서 Cron 구성도 반환되지 않았다. 이를 근거로 다른 운영 정기 작업의 존재 여부까지 단정하지 않는다. **이번 예약금 전용 운영 지속 실행은 미활성/미검증**이며 아래는 승인 후 적용할 실행안이다.

승인 후 적용할 주기는 매분(`* * * * *`, UTC)이다. 한 번의 실행 경로:

`Vercel Cron → GET /api/cron/booking-deposit-expiry → runDepositMaintenance → pm_deposit_tick → 만료·재알림·시작 시 자동확정 → pending outbox의 매장별 공통 dispatcher`

- `CRON_SECRET` Bearer 없거나 틀리면 401. 비밀값은 운영 보안 설정에만 둔다.
- 매장별 인자는 개발의 한정 검사에만 사용하고, 운영 기본 호출에는 `shopId`를 넣지 않는다. 전체 호출도 **신규 원장 연결 예약만** 처리한다. 기존 예약 전체를 만료하는 옛 함수는 호출하지 않는다.
- `runDepositMaintenance`는 전역 호출에서도 대기 중인 매장 최대 100개 행을 읽고 중복 매장을 합쳐 발송 큐를 처리한다. 매장당 20개씩 처리하므로 적체량과 60초 함수 한도를 관찰해야 한다. 무한 반복·자동 외부 재시도는 넣지 않았다.
- SQL 행 잠금/상태 조건과 outbox claim으로 동시 실행·중복 처리를 막는다. 외부 결과 불확실/processing 잔류는 자동 재발송하지 않고 확인 후 수동 정리한다.
- 오너 재알림은 앱의 기존 예약금 확인 알림 배너/감사 이벤트다. 별도 오너 카카오 알림톡을 보낸다는 뜻이 아니다.
- 다음 분 실행이 지연될 수 있다. 초 단위 정시 보장을 주장하지 않으며, 예약 시작 직전·직후 신규 예약 경합과 겹침 방지도 DB에서 별도로 유지한다.

[Vercel 공식 제한](https://vercel.com/docs/cron-jobs/usage-and-pricing)에 따르면 매분 실행은 Pro/Enterprise 조건이다. 이번 읽기 전용 조회에서 팀 요금제가 확인되지 않았으므로 미확인이다. 요금제 변경·유료 기능·작업 활성화는 별도 승인이 필요하다. [Cron 관리 안내](https://vercel.com/docs/cron-jobs/manage-cron-jobs)에 따라 `CRON_SECRET`, 활성 작업, 실행 로그, 실패·중복 호출을 승인 후 실제 운영에서 검증해야 한다. 이전 배포로 롤백해도 Cron이 자동 원복된다고 가정하지 않는다.

## 이번에 확인한 실행 증거와 한계

- 개발 Next 장기 프로세스의 15초 interval과 Vercel의 지속 실행은 다른 것이다. 로컬 프로세스가 꺼지면 개발 interval도 종료된다.
- 개발 전용 매장으로 신규 공통 실행 함수를 실제 개발 DB에 한 번 호출했다. 전역 outbox 처리·오류 차단은 모의 테스트 4건을 통과했다.
- 개발 HTTP 경로는 `CRON_SECRET` 미설정으로 401을 확인했다. 인증된 HTTP Cron 및 운영 지속 실행을 통과했다고 보고하지 않는다.
- 기존 단계의 실제 interval 만료·재알림·시작 확정 검증 기록은 별도 구현 보고서에 있다. 이번 수동 호출 결과로 그 기록을 대체하거나 운영 자동 실행을 증명하지 않는다.

## 알림톡 읽기 전용 결과

2026-10-18 쏘다 공식 API의 목록·상세만 조회했다. 릴레이의 로컬 GET 경로는 연결 불가였고 기존 보안 저장소의 자격 증명을 메모리에서만 사용해 공식 조회 API로 확인했다. 등록·검수 제출·설정 변경·실제 발송은 하지 않았다.

| 목적 | 확인 결과 | 운영 전 남은 조치 |
| --- | --- | --- |
| 예약금 요청/재요청 v1 | APR/R, 현재 공통 본문·변수·버튼·PC/모바일 예약 링크 일치 | 개발/운영 공용 DB에 해당 alias 매핑 없음. 실제 런타임 릴레이 매핑은 조회 불가이므로 정상 연결 단정 불가 |
| 예약금 요청 v2 | REQ/R, 버튼/링크 일치, 본문은 현 계약과 불일치(계좌·금액 안내 순서) | 승인 완료 후 최종 본문과 코드 계약을 맞추고 매핑 검증. 미승인 버전으로 임의 전환하지 않음 |
| 예약 확정 | 운영 공용 매핑 `booking_confirmed_v2`, APR, 본문·버튼 일치. 상세 status S는 현재 코드의 활성 허용값 밖 | 실제 제공사 활성 상태 확인 필요. S 의미를 추정해 허용 범위를 넓히지 않음 |
| 매장 귀책 취소 | 운영 공용 매핑 `booking_cancelled_v4`, APR/R, 본문·버튼 일치 | 승인 후 런타임 경로/실발송 별도 검증 |
| 고객 취소·입금 기한 만료·환불 완료 | 전용 alias 매핑/승인 계약 없음 | 전용 템플릿 승인·공통 계약·코드 연결 필요. 기존 매장 귀책 취소 문구로 대신 보내지 않음 |

운영 공용 템플릿 매핑 테이블만 읽기 전용 조회했으며 운영 고객 데이터는 조회·복사하지 않았다. 로컬 개발 환경에는 구버전 확정/취소 매핑이 남아 있다. 개발 모의 발송 성공을 운영 매핑 정상/실발송 성공으로 해석하면 안 된다. 실제 Vercel 환경변수·운영 릴레이의 현재 mapping 전체는 미확인이다.

전체 OFF와 고객 수신 거부는 각각 실제 개발 API에서 차단됐다. force는 둘을 우회하지 못한다. 예약금 대상 선정과 수신 여부는 별개이며 차단된 고객도 웹 예약 확인에서 계좌/기한/상태를 확인한다. 실발송은 전부 미실행이다.

## 환불 일치성

개발 가상 매장의 `24시간 이상 전 100% / 24시간 미만 50%` 예시로 다음을 검증했다.

- 고객 예약 전 고지와 동의 체크, 서버의 정책 버전 검증, 예약 준비의 동의 시각/버전/정책 스냅샷.
- 고객 취소 API가 2만원 중 1만원 환불·1만원 수수료를 계산.
- 이후 설정 변경에도 기존 예약의 환불 규칙·계좌·금액·기한은 유지.
- 매장 귀책 취소 전액 환불, 최종 요금 2만5천원/확인 입금 3만원의 차감 및 초과 5천원 반환.
- 취소 예약을 캘린더에서 다시 열어 기존 상세에서 가상 직접 환불 완료 기록 저장.

위 비율은 전용 테스트 데이터이며 실제 매장 정책을 바꾼 것이 아니다. 고객 신고만으로 금전이 생기지 않고 실제 확인액 기준으로만 차감/환불한다. 고객 환불 계좌는 수집하지 않는다. **법적 적합성 검토는 완료되지 않았다.** 소비자분쟁해결기준·사전 고지·실제 매장 약관의 법적 검토는 기술 검증과 별도로 운영 반영 전 확인해야 한다.
