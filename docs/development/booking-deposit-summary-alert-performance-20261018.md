# 예약금 화면·확인 알림·조회 성능 개선 (개발 환경)

## 결과

로컬 코드와 `petmanager-dev (qefxdtmdtvnzgupmjlom)`에만 반영했다. 운영 DB·배포·push·실제 메시지 발송은 실행하지 않았다. 새 원장이나 사업 정책은 만들지 않았다.

### 상단 확인 알림

- 전체 너비 환불 배너를 기존 PC 헤더 / 모바일 오늘 헤더·예약 조회 툴바의 `확인 필요 N건`으로 대체했다.
- 입금 확인 또는 환불 항목을 누르면 기존 예약 상세를 연다. 같은 보호자·날짜 공유 원장은 한 건으로 집계한다.
- `확인`은 사용자별 알림 읽음만 저장한다. 실제 예약/입금/환불 상태와 이벤트는 바뀌지 않는다. 새로고침 후에도 같은 알림은 다시 나오지 않는다.
- 새 신고/기존 확인 재알림/새 환불 계산의 식별값이 달라지면 새 알림으로 표시한다. 실제 업무가 끝나면 대상 조회에서 제외한다. 기존 확인 기한을 넘겨 재알림된 경우에만 `기한 경과`를 붙인다.
- `booking_deposit_notice_reads`는 서비스 역할만 읽기·삽입 가능하며 RLS를 유지한다. 앱은 기존 오너/매니저 권한과 매장 범위 검사를 거친다. 알림톡과 무관한 인앱 확인 기록이다.

### 기본 표시 / 상세 표시

| 상태 | 기본 표시 |
|---|---|
| 입금 대기 | 요청액·입금 상태·입금 확인 동작 |
| 고객 신고 | 신고 입금자명·실제 확인 총액 입력·확인 버튼 |
| 확인 완료 | 이번 예약 차감 예정액·실제 남은 결제액 |
| 환불 대기 | 미처리 환불액·직접 송금 후 완료 기록 |
| 정산 완료 | 남은 결제액·환불 완료액 결과 |

요청액·실제 확인액·승계 포함 총액·배분액·이미 차감한 액수·가용 잔액·수수료는 기존 `추가 처리·정산 내역`에 보존했다. 처리 이력은 펼칠 때 조회한다. 입금 정정/확인 취소/일정 변경/환불 버튼은 유지했다. 실제 미입금 경고와 미처리 환불액, 실제 추가 결제액을 숨기지 않는다. 미정 금액은 0원으로 표시하지 않는다. 고객에게 오너 정산 내역은 노출하지 않는다.

## 측정과 원인

개발 서버, 동일한 마루 예약 `0d58fdcd-2c61-473d-a8c7-aeb65aeb0236`, PC1440×1000에서 비교했다. DB 상태는 완료/확인액30,000원/차감25,000원/환불완료5,000원으로 동일하다. 초기 화면 클릭부터 요약 DOM 표시까지 측정했고, 별도 no-store API 요청4회 중 2~4회를 재조회로 구분했다. 브라우저/서버 캐시를 전부 비운 콜드 시작이나 p95/실기기 수치는 아니다.

| 항목 | 개선 전 | 개선 후 |
|---|---:|---:|
| 최초 상세 열기→요약 표시(각1회) | 3,943ms | 1,350ms |
| 해당 최초 열기의 API 요청 수 | 2 | 1 |
| 별도 API 첫 측정(이미 상세를 연 뒤) | 1,850ms | 1,165ms |
| API 재조회3회 | 1,849 / 1,824 / 1,867ms | 1,016 / 997 / 1,006ms |
| 샘플 응답 문자 수 | 4,441 | 3,308 |
| 기본 응답 처리 이력 | 6건 | 미조회; 펼치면6건 |

실제 서버 fetch 추적에서 기존 경로는 만료 판정, 예약/준비, 전체 원장 이력, 승계 가능액, 과거 환불, 고객 설정, 정책, 오너 규칙을 대부분 직렬로 기다렸다(10요청/1,469ms). 독립 요청을 병렬화하고 긴 상세 이력·다른 날짜 내역을 지연 조회하도록 했다(요약8요청/1,006ms). 네트워크 변동이 있어 개별 요청 시간은 전후 동일하지 않다. 상단 알림은 예약 상세의 선행 요청이 아니며, 그 조회에서 불필요한 동기 만료 실행을 제거했다. 기존 시간 작업 자체를 새로 활성화하지 않았다.

공유 읽기 훅은 동일 뷰의 진행 중 요청을 합치고, busy/onLedger 콜백 재생성으로 재조회하지 않는다. 예약금이 없는 뷰는 주기 조회하지 않는다. 예약/요청 세대/원장 버전 검사를 통해 이전 예약·변경 전 응답을 버린다. 금액 캐시는 추가하지 않았다. 변경 응답을 즉시 적용하고 같은 앱 origin의 다른 열린 상세·상단 알림을 무효화해 재조회한다. 다른 기기/별도 origin의 갱신은 기존 주기·focus 재조회이며 실기기 즉시 동기화 보장은 검증하지 않았다.

모바일은 브라우저 에뮬레이션390×844(추가430/320폭)에서 화면·처리·overflow를 확인했다. 모바일 개선 전후 시간은 별도로 측정하지 않았으며 PC 수치를 모바일 수치로 대신하지 않았다.

## 실제 검증

- 실제 사용자 권한 API/브라우저7항목 통과: 원장 단위 중복 집계 없음, 읽음 후 숨김, 읽음과 돈/예약 상태 불변, 새로고침 유지, 해당 예약으로 이동, 이력 지연 조회, 타 매장 조회/읽음 거부.
- 실제 UI 정정5항목 통과: 총액 절대값 저장, 공유 예약 배분 합계, 다른 열린 공유 상세의 무효화/focus 갱신, 원래 총액 복귀와 기록 보존, 다른 상세에서도 복귀 확인.
- 오너 모바일6항목 통과: 환불액/버튼, 모의 환불 직후 요약 갱신, 환불 처리 후 알림 해제,430/390/320 가로 넘침 없음.
- 모바일 헤더3항목 통과: 키보드로 메뉴 항목에 초점 후 Escape 닫기/버튼 초점 복귀, 좁힌 담당자 필터 조작 유지, 예약 조회 툴바 알림.
- 지연 응답 브라우저2항목 통과: 이전 예약 API 응답을 CDP로 보류하고 다음 예약을 연 뒤 해제했다. 대기 중 이전 금액 표시 없음 / 늦은 응답이 새 예약 금액을 덮어쓰지 않음.
- 개발 DB 트랜잭션 검증 통과·롤백: 공유 총액/배분, 요약과 전체 금액 동등, 읽음의 금전 상태 불변, 새 알림 버전 재표시, 공유 알림 중복 방지.
- UI 계약7개, 확인 취소·모바일 CORS 관련9개, 모바일 예약 흐름 계약6개, workspace10개·공유 UI43개, 웹/모바일 타입 검사 통과.
- 처음 실패한 검사는 테스트 경로·React data 속성·금액 문자열 부분 일치(5,000이25,000에도 포함됨)와 DOM 자동 클릭의 초점 조건을 수정했다. 확정 정책을 바꾸거나 실패 검사를 삭제하지 않았다. 실제 배분은 첫 예약의 미용 요금25,000원을 우선 충족하므로21,000원 전체가 첫 예약에 배분되는 것이 기존 정상 동작이었다.
- 이전에 통과한 전체 고객 예약/신고 흐름을 다시 생성하지 않았다. 입금 확인 버튼은 신고 상태의 실제 화면과 UI 계약으로 확인했고, 이번에 그 전체 흐름을 새로 수행했다고 주장하지 않는다.

## 이미지·실행 근거

`.codex-work/deposit-summary-alert-performance-20261018/`에 전후 PNG, 측정 JSON, API/브라우저·DB 검사, 적용 영수증과 원복 SQL이 있다. PC 전후1440×1000 / 모바일 전후390×844는 동일 마루 예약·동일 정산 상태다. PC 전 이미지에는 기존 대형 환불 배너도 포함된다. 상단 목록 수는 검증 과정의 읽음1건·환불 완료1건으로 최종4→2건이므로 예약금 정산 상태 비교와 구분한다. 모바일 기존 화면에는 이 신규 확인 목록이 없었다.
