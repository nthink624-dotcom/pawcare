# PetManager 장애 대응 최소 런북

이 문서는 장애가 발생했을 때 고객 데이터와 운영 DB를 더 훼손하지 않으면서 상태를 확인하고 복구하는 순서를 고정한다. 원인과 대상이 확인되지 않은 상태에서 재배포·DB 변경·데이터 삭제를 반복하지 않는다.

## 1. 장애 선언 기준

- 운영 도메인이 5분 이상 HTTP 5xx 또는 연결 실패를 반환한다.
- `/api/healthz`가 200이 아니거나 `/api/readyz`가 503을 반환한다.
- 예약 저장, 결제 웹훅, 알림톡 발송 중 하나가 반복 실패한다.
- 다른 매장의 고객·예약·사진이 보일 가능성이 제기된다.

## 2. 첫 10분: 증거 보존

1. 발생 시각(KST), 도메인, 사용자 동작, 오류 문구, 영향 매장을 기록한다.
2. `/api/healthz`와 `/api/readyz` 응답 상태·응답 본문에서 고객 데이터가 아닌 상태 필드만 보존한다.
3. 최근 배포 ID와 Git 커밋을 확인한다. 중간 상태(`Building`, `Queued`)를 성공으로 판단하지 않는다.
4. Supabase 대상은 먼저 확인한다.

```powershell
npm run check:supabase-cli-target:dev
```

운영 DB에 연결하거나 운영 마이그레이션을 실행하려면 운영 ref와 변경 사유를 별도 승인받는다.

## 3. 분기별 대응

### 앱 전체 장애

- 새 배포를 중지한다.
- 마지막으로 검증된 배포 alias와 현재 배포를 비교한다.
- 원인이 코드 배포로 확인된 경우에만 승인된 롤백을 실행한다.
- 롤백 후 `/api/healthz`, `/api/readyz`, 로그인 smoke를 다시 확인한다.

### DB 준비 상태 실패

- DB 마이그레이션을 재실행하지 않는다.
- Supabase Dashboard의 프로젝트 상태와 provider 장애 여부를 확인한다.
- 개발 환경이면 `npm run verify:supabase-rls:dev`로 대상과 RLS 상태를 확인한다.
- 운영 복구는 백업/PITR 증거와 RTO 판단 후 승인된 절차로만 진행한다.

### 결제·알림톡 웹훅 실패

- 같은 이벤트를 수동으로 반복 발송하지 않는다.
- 서명 검증 실패인지, provider API 실패인지, 내부 동기화 실패인지 분리한다.
- 결제는 payment ID, 알림은 notification ID를 기준으로 멱등성 상태를 확인한다.
- 운영 provider 대시보드의 재전송은 중복 방지 상태 확인 후 승인받아 실행한다.

### 테넌트 격리 의심

- 해당 계정·매장의 접근을 일시 제한하고 증거를 보존한다.
- 관련 API와 RLS 정책을 확인한다.
- 고객 데이터 삭제나 수정으로 문제를 숨기지 않는다.
- 영향 범위와 재현 조건을 확인한 뒤에만 패치·복구한다.

## 4. 복구 후 확인

- 핵심 로그인·예약 조회·예약 저장·알림 기록·결제 상태 조회를 집중 검사한다.
- `/api/healthz` 200과 `/api/readyz` 200을 확인한다.
- 다른 매장 ID를 사용한 격리 테스트가 통과하는지 확인한다.
- 장애 시각, 원인, 영향, 복구 시각, 재발 방지 변경을 증거 문서에 기록한다.

## 5. 금지 사항

- 개인 Chrome 프로필이나 운영 계정 세션을 강제로 종료하지 않는다.
- 운영 DB에서 `TRUNCATE`, 임의 삭제, 직접 SQL 수정을 하지 않는다.
- 비밀키·토큰·전화번호·고객 사진을 로그나 채팅에 복사하지 않는다.
- 백업이 실제로 복구되는지 확인하지 않은 채 “복구 가능”이라고 보고하지 않는다.
