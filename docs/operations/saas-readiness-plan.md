# SaaS 운영 준비 계획

이 문서는 PetManager를 단순히 기능이 동작하는 앱이 아니라, 여러 매장이 안심하고 계속 사용하는 SaaS로 운영하기 위한 기준과 순서를 고정한다. 코드에 있는 안전장치와 실제 운영 계정에서 활성화된 설정은 서로 다른 상태이므로, 확인하지 않은 항목을 완료로 표시하지 않는다.

## 완료 기준

- 매장(tenant) 간 데이터가 섞이지 않고, 모든 운영 데이터 접근이 인증·권한·매장 범위로 제한된다.
- 장애가 나도 복구 목표(RPO 24시간 이내, RTO 4시간 이내)를 충족하고 실제 복구 리허설 기록이 있다.
- 결제·알림톡·웹훅은 중복 요청, 지연, 재시도를 견디며 운영자가 실패 건을 찾고 재처리할 수 있다.
- 배포 전에 대상 환경·마이그레이션·인증·핵심 플로우를 자동 검사하고, 실패하면 배포하지 않는다.
- 개인정보 보관·삭제·내보내기·제3자 전송 범위가 문서와 실제 구현에서 일치한다.
- 장애·보안사고·결제 실패에 대한 담당자, 알림 경로, 롤백 절차가 정해져 있다.

## 우선순위

### P0 — 유료 고객을 받기 전 막아야 하는 것

1. **운영 환경 목록 고정**: 웹·모바일·API·Supabase·R2·결제·알림톡의 운영 URL, 프로젝트 ref, 환경변수 소유자와 변경 절차를 한 표로 관리한다. 비밀값 자체는 문서에 넣지 않는다.
2. **DB와 미디어 복구**: 운영 Supabase의 일일 백업 또는 PITR, R2 객체 보존·삭제 정책, 암호화된 오프사이트 논리 백업, 분기별 격리 복구 리허설을 활성화하고 증거를 남긴다. DB 백업만으로 Storage 객체가 복구된다고 가정하지 않는다.
3. **테넌트 격리 회귀 테스트**: 다른 `shop_id`의 고객·예약·사진·결제 정보를 읽거나 수정할 수 없는 테스트를 API와 RLS 양쪽에서 수행한다.
4. **결제 안전성**: 웹훅 멱등 키, 서명 검증, 재시도, 구독 상태 재조정(job), 환불·해지·실패 상태를 운영 화면에서 확인할 수 있게 한다.
5. **장애 대응 최소 세트**: `/api/healthz`(프로세스), `/api/readyz`(DB·필수 외부 의존성), 요청 상관관계 ID와 배포 후 endpoint smoke gate를 코드에 추가했다. 다음으로 오류 추적·알림 채널, 롤백 명령, 담당자 연락망을 고정한다.
6. **개인정보 운영 정책**: 보관기간, 고객 요청에 대한 내보내기/삭제, 사진·전화번호·알림톡·AI 전송의 목적과 제3자 제공을 실제 흐름과 맞춘다.

### P1 — 베타 운영을 안정화하는 것

- 알림톡·결제·이미지 분석을 큐/재시도 가능한 작업으로 만들고, 실패 사유·마지막 시도·재처리 버튼을 제공한다.
- 관리자 감사 로그(누가, 어느 매장에, 어떤 작업을 했는지)는 `/admin/audit`에서 검색 가능하게 구현했다. 운영 배포 readback과 실제 담당자 운영 절차 연결은 남아 있다.
- IP·계정·매장 단위 rate limit, 로그인/복구 시도 제한, 웹훅 replay 방어를 적용한다. 고객 예약 링크 복구에는 IP·전화번호·매장 단위 제한과 로컬 fallback 상한을 반영했으며, 다중 인스턴스 공용 primitive readback이 남아 있다.
- CI에서 typecheck, lint, 계약 테스트, 데이터 안전 가드, 환경 대상 가드, 핵심 smoke를 한 번에 실행한다.
- 고객지원 runbook(가입, 매장 초대, 번호 변경, 환불, 탈퇴, 데이터 복구 요청)을 작성한다.

### P2 — 매장 수가 늘 때 필요한 것

- 매장별 사용량/쿼터와 비용(스토리지, 이미지 분석, 알림톡, 결제) 대시보드.
- 장시간 작업용 작업 큐와 dead-letter queue, 보정 작업(reconciliation) 스케줄러.
- SLO: API 성공률, p95 지연, 알림 전달률, 결제 웹훅 처리 지연, 복구 시간.
- 부하 테스트, 인덱스·쿼리 관찰, PITR 보존 기간 확대, 용량 증설 절차.

## 30/60/90일 실행 순서

### 0–30일: 운영 출발선

- 운영 계정 readback으로 Supabase 백업/PITR, R2 보존, Vercel 환경변수, 결제·알림톡 웹훅을 확인한다.
- `/healthz`·`/readyz`, 오류 추적과 장애 알림을 추가한다.
- 테넌트 격리·인증 만료·웹훅 멱등성 계약 테스트를 릴리스 게이트에 넣는다.
- 운영/테스트용 데이터와 비밀값이 섞이지 않는지 점검한다.

### 31–60일: 실패를 복구할 수 있게 만들기

- 알림톡·결제·미디어 작업의 재시도/실패 큐와 운영자 재처리 흐름을 완성한다.
- 데이터 내보내기·삭제 요청을 운영에 연결하고, 구현된 관리자 감사 로그를 담당자 절차와 연결한다.
- 격리된 테스트 프로젝트로 DB + R2 복구 리허설을 수행하고 RTO/RPO를 측정한다.

### 61–90일: 반복 가능한 운영

- CI/CD에 전체 릴리스 게이트와 승인 단계를 고정한다.
- 사용량·비용·SLO 대시보드와 월간 운영 리뷰를 만든다.
- 분기별 복구 훈련, 권한 검토, 의존성·비밀값 교체 일정을 캘린더화한다.

## 이번 작업에서 자동 확인하는 범위

`npm run check:saas-readiness`는 비밀값이나 운영 DB를 읽지 않고 다음만 검사한다.

- 핵심 운영 문서·안전 스크립트·마이그레이션 디렉터리가 존재하는지
- root/workspace에 릴리스 전 환경·데이터 안전·인증·신뢰성 검사가 연결되어 있는지
- 개발 Supabase 대상 가드와 운영 대상 명시적 승인 가드가 유지되는지

이 검사는 “운영 계정에서 백업이 실제로 켜졌다”거나 “결제 웹훅이 등록됐다”는 증명이 아니다. 그런 항목은 대시보드 readback과 복구 리허설 증거가 있어야 완료로 바꾼다.

## 승인 게이트

다음은 대표의 별도 승인이 있어야 실행한다.
