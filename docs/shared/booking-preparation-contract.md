# 예약 준비 공통 계약

정본 타입: `apps/shared/contracts/booking-preparation.ts`.
마이그레이션: `supabase/migrations/20261006011111_booking_preparation_policies.sql`, `supabase/migrations/20261006190000_booking_consent_template_archive.sql`.
기본 예약 준비 마이그레이션은 2026-10-06 petmanager-dev에 적용됐으며 운영에는 미적용이다. 동의서 보관 후속 마이그레이션은 로컬 소스만 추가했고 아직 어떤 DB에도 적용하지 않았다.

## 저장과 권한

- `shop_booking_policies`: 매장 정책, 문서 템플릿 버전, 설정 버전.
- `booking_preparations`: 예약별 정책·문서·서명·입금·환불·처리 이력. 버전 비교로 동시 변경을 차단한다.
- `guardian_booking_conditions`: 매장·보호자별 다음 예약 조건과 변경 사유.
- 세 테이블은 RLS를 켜고 anon/authenticated 직접 접근을 모두 철회한다. 서버 API만 서비스 역할을 사용한다.
- 오너/매니저 API는 `requireOwnerShop`과 역할 검사로 매장을 제한한다.
- 보호자 API는 만료 확인된 `manage` 토큰의 매장·보호자·반려동물·예약 범위를 검사한다. 오너 메모·처리자·발송 이력·문서 예외 메모는 응답에서 제외한다.
- 서명은 최대 40획, 획당 1,500개 점, 전체 12,000개 점으로 제한한 좌표 배열이다. 좌표는 0~1 범위이며 HTML/SVG를 입력받지 않는다.
- 서명 완료 문서는 RPC에서 원본 변경을 차단한다. 동일 버전·매장·보호자·반려동물의 재사용 가능 문서만 재사용한다.
- 예약/반려동물 삭제만으로 서명 이력을 지우지 않는다. 매장·보호자 데이터 삭제 시 관련 기록은 삭제한다. 회원 탈퇴 경로와 보존 예외 정책의 연결은 별도 출시 전 확인 항목이다.
- 기본 미용 동의서는 그루머노트 표준 양식의 건강·행동 확인, 안전을 위한 범위 조정, 응급 연락, 추가 작업·비용 사전 동의 항목을 참고해 PetManager 문안으로 구성한다. 포괄 면책·무조건 환불 불가·유기/장기 미수령 조항은 복사하지 않고, 사진·홍보 활용 동의도 별도 선택 문서로 분리한다.
- 기본 동의서는 삭제하거나 보관할 수 없다. 직접 만든 양식은 `archivedAt`으로 보관해 신규 예약 요청 대상에서 제외하며, 오너가 복구할 수 있다. 보관 전 예약에 이미 만들어진 서명 요청과 서명 원본은 기존 예약 스냅샷을 유지한다.
- 정책 편집 화면은 저장 전 양식 전환·취소를 확인하고, 기본 양식의 표준 문안 복원을 제공한다. 현재 정책 행은 최신본만 보유하므로 일반 편집 전 버전의 무서명 사용자 양식은 별도 이력 저장 전까지 복원 대상이 아니다.
- 기본 요청 대상은 현재 버전에 서명하지 않은 반려동물이다. `scope=pet`에서 같은 매장·반려동물·문서 ID·버전의 서명이 있으면 예약에 완료 상태로 연결해 다시 요청 목록에 띄우지 않는다. 알림톡 발송은 예약별 오너 선택이며 자동 발송하지 않는다. 새 문서 버전은 새 동의로 취급한다.

## API

- `GET/PUT /api/owner/booking-policy`: 정책 조회·버전 비교 저장. 문서 내용 변경 시 버전 증가.
- `GET/POST /api/owner/booking-preparation`: 예약 준비 조회·입금 확인·면제·수동 환불 기록·동의서 추가·예외·승인·취소·노쇼·정정·고객별 다음 예약 조건.
- `GET /api/owner/booking-preparation?archive=1`: 서명 이력 페이지 조회, UUID cursor, 20개 예약 단위. 서명 원본은 예약 삭제 후에도 조회 가능.
- `GET/POST /api/customer-booking-preparation`: 보호자 본인 범위 조회·서명·입금 신고·취소 요청·요청 알림 수신 설정.
- `GET /api/booking-policy`: 공개 예약 전 안내용 최소 정책과 버전. 계좌·미사용 문서·내부 정보는 공개하지 않는다.
- 고객 예약 생성 payload에 `bookingPolicyVersion`, `bookingPolicyAccepted` 추가. 정책이 있는 매장은 확인 및 버전 일치를 요구한다. DB에서 삽입 시 다시 버전을 비교한다.
- `guardians.notification_settings.consent_request_enabled`, `.deposit_request_enabled` 추가. 기본 true, 전체 enabled=false 우선. 수신 거부가 예약금 면제를 의미하지 않는다.

## 예약·금액 상태

- 예약금 필수 또는 고객 승인 필요 예약은 `appointments.status=pending`. 담당자 시간 창을 점유하며 기존 shop/staff 트랜잭션 잠금을 유지한다.
- 입금 신고 `reported`는 확인 완료가 아니다. 오너가 실제 금액·입금자명을 확인해야 `confirmed`가 된다.
- 예약금 필수 예약은 입금 확인·면제 후 자동 확정한다. 별도 승인 조건이 있는 예약은 오너가 승인한다. 미확인 필수 예약금은 승인·미용 시작을 DB에서 차단한다.
- 필수 문서 미완료는 미용 시작을 DB에서 차단한다. 승인에는 동의서 서명을 요구하지 않는다.
- 기납부 잔액 = 입금 확인액 - 실제 환불 기록액. 잔금 = max(서비스 최종가 - 기납부 잔액,0).
- `refund_record`는 실제 계좌 반환을 기록한다. 송금·PG 환불 실행 기능이 아니다. PG 예약금 결제·자동 환불은 아직 미연결.
- 취소/노쇼는 준비 상태와 한 트랜잭션에서 저장한다. 기존 상태 변경 경로도 종료된 예약금 요청을 닫는다.
- 노쇼는 시간이 지난 확정 예약만 처리한다. 정상·늦은 취소·미납 취소를 노쇼 횟수에 합산하지 않는다.
- 미납 기한 경과는 표시하며 자동 취소하지 않는다. 오너가 유지·취소를 결정한다.

## 알림톡

- 오너·고객 예약이 실제 확정되었을 때 승인된 booking_confirmed 계약과 공통 발송기를 사용한다. 대기 예약에는 확정 메시지를 보내지 않는다.
- 예약금/동의서 요청은 발송 선택과 처리 이력을 별도로 둔다. 새 템플릿이 승인·연결되지 않은 현재 상태에서는 blocked로 기록한다.
- 수신 거부를 먼저 검사하며 승인 템플릿이 없는데 sent로 표시하거나 다른 채널로 자동 우회하지 않는다.
- 현재 booking_cancelled 문구는 매장 사정 취소에만 사용한다. 고객/늦은 취소·노쇼 안내에는 새 템플릿이 필요하다.
- 자동 방문 안내의 기존 예약당 최대 1회 규칙은 유지한다.

## 적용·검증 상태
