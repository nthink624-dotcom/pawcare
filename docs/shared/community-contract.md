# Member community contract (2026-11-09)

- Web `/owner?screen=community` and mobile community tab render `apps/shared/components/community/community-board.tsx`. Both consume the same web `/api/owner/community` through the existing authenticated API client. No mobile-only data or browser persistence.
- Access requires verified Auth identity, current shop membership (owner/manager or active bound staff), and existing account/subscription guards. Server rejects null identities and ignores client-supplied identity. Community posts are intentionally shared between participating shops; customer, reservation, contact and care-report data are never read or automatically attached.
- GET `?shopId=&q=&category=&page=` returns `{viewer:{nickname},blockedUsers:[{id,nickname}],posts,hasMore,page}`. Add `postId` for `{post,comments,hasMore,page}`. Twenty rows per page, deterministic time/id ordering. Search matches literal title/body text. Categories: operations, knowledge, lounge, feedback. Rows expose nickname and isMine, never Auth/other-shop IDs.
- POST actions: create_post, update_post (expectedUpdatedAt required), delete_post, create_comment, delete_comment, profile, report, block, unblock. Titles 1–100, body 1–10000, comments 1–2000, nickname 2–24, reason 2–500. Stable post/comment UUIDs make retries idempotent. Updates/deletes require authorship. Limits: 20 posts, 100 comments, 20 reports per user/day. Blocks mutually hide posts/comments. Issued image links may remain usable for 60 seconds.
- Photo writes: multipart payload + photos, streaming request cap 3.4MB, maximum 3 photos. Browser re-encodes selected JPG/PNG/WebP. Server independently decodes, strips metadata and encodes WebP, 1600px and <=1MB each. Durable IDs: community_media_assets.media_asset_id. Existing care-media IDs and URLs are not accepted. Private bucket community-images, restrictive browser policy, signed-URL batch with 60-second expiry. API responses private/no-store.
- Tables: community_profiles, community_posts, community_comments, community_media_assets, community_blocks, community_reports, community_media_deletions. Every table has RLS; browser grants revoked. Invoker-rights community_dispatch is service_role-only, checks membership again, serializes per-user mutations, commits content/media metadata atomically.
- Internal community_private.queue_media_deletion is a revoked, fixed-empty-search-path definer trigger solely for queuing photo paths during deletion cascades, including Auth deletion. No public definer API. Content remains until author/account deletion or moderation. Post deletion cascades comments/media rows; account deletion cascades authored content. Durable cleanup queue retries Storage deletion on community reads/writes (50 at a time); failed operations retain queue rows. This is opportunistic cleanup, with no guaranteed purge interval. Upload error cleanup requires a successful DB read proving objects are unattached.
- /admin/community and /api/admin/community use the existing independently verified active admin session. Reports support reviewed hide/dismiss actions with admin/time audit. Target type persists after deletion, so a deleted-comment report cannot hide its parent. All user content is rendered as plain text.
- No customer notifications, production migration, external publication or app-store upload is part of the local implementation. Release requires separate approval.
