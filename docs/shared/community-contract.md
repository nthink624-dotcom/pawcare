# Member community contract (2026-11-09)

- Web `/owner?screen=community` and mobile community tab render `apps/shared/components/community/community-board.tsx`. Both consume the same web `/api/owner/community` through the existing authenticated API client. No mobile-only data or browser persistence.
- Access requires verified Auth identity, current shop membership (owner/manager or active bound staff), and existing account/subscription guards. Server rejects null identities and ignores client-supplied identity. Community posts are intentionally shared between participating shops; customer, reservation, contact and care-report data are never read or automatically attached.
- GET `?shopId=&q=&category=&page=` returns `{viewer:{nickname},blockedUsers:[{id,nickname}],posts,hasMore,page}`. Add `postId` for `{post,comments,hasMore,page}`. Twenty rows per page, deterministic time/id ordering. Search matches literal title/body text. Categories: operations, knowledge, lounge, feedback. Rows expose nickname and isMine, never Auth/other-shop IDs.
- POST actions: create_post, update_post (expectedUpdatedAt required), delete_post, create_comment, delete_comment, profile, report, block, unblock. Titles 1–100, body 1–10000, comments 1–2000, nickname 2–24, reason 2–500. Stable post/comment UUIDs make retries idempotent. Updates/deletes require authorship. Limits: 20 posts, 100 comments, 20 reports per user/day. Blocks mutually hide posts/comments. Issued image links may remain usable for 60 seconds.
- Photo writes: multipart payload + photos, streaming request cap 3.4MB, maximum 3 photos. Browser re-encodes selected JPG/PNG/WebP. Server independently decodes, strips metadata and encodes WebP, 1600px and <=1MB each. Durable IDs: community_media_assets.media_asset_id. Existing care-media IDs and URLs are not accepted. Private bucket community-images, restrictive browser policy, signed-URL batch with 60-second expiry. API responses private/no-store.
- Tables: community_profiles, community_posts, community_comments, community_media_assets, community_blocks, community_reports, community_media_deletions. Every table has RLS; browser grants revoked. Invoker-rights community_dispatch is service_role-only, checks membership again, serializes per-user mutations, commits content/media metadata atomically.
- Internal community_private.queue_media_deletion is a revoked, fixed-empty-search-path definer trigger solely for queuing photo paths during deletion cascades, including Auth deletion. No public definer API. Content remains until author/account deletion or moderation. Post deletion cascades comments/media rows; account deletion cascades authored content. Durable cleanup queue retries Storage deletion on community reads/writes (50 at a time); failed operations retain queue rows. This is opportunistic cleanup, with no guaranteed purge interval. Upload error cleanup requires a successful DB read proving objects are unattached.
- /admin/community and /api/admin/community use the existing independently verified active admin session. Reports support reviewed hide/dismiss actions with admin/time audit. Target type persists after deletion, so a deleted-comment report cannot hide its parent. All user content is rendered as plain text.
- No customer notifications, production migration, external publication or app-store upload is part of the local implementation. Release requires separate approval.

## Feed reactions and private saved posts (2026-11-11)

- The member feed has no search field, category/status filters or topic recommendations. Existing q/category API parameters remain compatible; they are not exposed in the feed. New plain posts use the existing lounge category internally; editing preserves the stored category.
- Every post in list/detail adds `likeCount:number`, `liked:boolean`, `saved:boolean`. Counts aggregate likes only. The two flags belong to the server-verified account. No saver identities, other accounts' save flags or bookmark counts are exposed.
- POST `{action:"like"|"save",postId,active:boolean}` sets the requested state instead of toggling blindly. The result includes `{id,success:true,reaction:{id,likeCount,liked,saved}}`. Unique account/post keys and the existing per-user transaction lock make duplicate retries idempotent. Identity is never accepted from the request body.
- GET `savedOnly=true` lists only the verified account's saved, currently visible posts, ordered by saved time descending then post ID. It uses the same twenty-row pagination, private/no-store response and signed-image resolution. `savedOnly=false` is the ordinary feed; invalid values are rejected.
- Web and mobile use the same server rows. No localStorage, device-only bookmarks, independent fallback data or download behavior is used. A failed interaction retains the previous displayed state and can be retried.
- `community_post_likes` and `community_post_saves` reference the existing community profile and post. Both have RLS enabled and browser grants revoked; service-role invoker RPCs enforce membership and hidden/block visibility. Profile/account or post deletion cascades reactions. Hidden/blocked posts are excluded from saved results and cannot receive interactions.
- The new migration and the existing member-community migration are local implementation artifacts until explicitly applied to a named hosted project. SQL-backed isolated tests are distinct from hosted readback.

## Korean nested comments (2026-11-11)

- The real shared detail screen uses `apps/shared/components/ui/reddit-nested-thread-reply.tsx`; web/mobile `src/components/ui` files re-export it. React, TypeScript, Tailwind and lucide-react already exist. The component follows existing scoped CSS/native controls, without installing a second UI framework or overwriting global Button/Card/Avatar primitives. It needs no context provider, stock images or external avatar service.
- `CommunityComment` adds `parentId:string|null`, `isPostAuthor:boolean`, `unavailable:boolean`, `score:number`, `vote:-1|0|1`. Author identity and the original-poster badge come from verified server rows, never item position or the caller. Korean actions: 댓글 등록, 답글 등록, 추천/비추천, 답글 접기/펼치기, 삭제, 신고, 차단. No dummy awards, share controls, users or local-only votes.
- POST `create_comment` adds optional nullable `parentId` (default null). A parent must exist, be visible and belong to the same post; a composite foreign key also enforces post ownership of the parent. Maximum stored path is eight comments; visual indentation stops after two nested levels. Stable retry UUIDs must match the same account/post/parent/body or return 409. Failed writes keep the draft and retry ID.
- POST `{action:"vote_comment",postId,commentId,value:-1|0|1}` sets the verified account's desired vote; zero removes it. Response includes `commentReaction:{id,score,vote}`. Only server-confirmed results update the UI. One account/comment primary key plus the existing user transaction lock prevents duplicate votes; counts aggregate signed values, without revealing voter identities.
- Detail pagination remains 20 visible comments in registration order, with their ancestor context included. Ancestors can repeat on later pages so replies retain context; `hasMore` describes new visible rows, not those contextual ancestors. Each path is bounded to eight levels. Hidden/blocked ancestors expose only a placeholder, timestamp and hierarchy, with no author/content/vote data. Hidden/blocked targets cannot receive replies or votes. Parent deletion detaches surviving child replies rather than deleting other authors' content. Post/account deletion cascades only the existing owned content and associated votes.
- `community_comment_votes` has RLS and no browser grants; invoker-rights internal RPCs are service-role-only. APIs remain authenticated and private/no-store. There is no production migration or hosted-development write implicit in this implementation. Apply the three canonical community migrations to a named project only after explicit authorization.

## Two panels and operator resources (2026-11-12)

- The shared board uses the available owner surface width with 24px desktop / 16px mobile outer padding. The web shell removes its additional inset for community only. The discussion feed is a single chronological column at every width, with no masonry/ResizeObserver layout. A separate scrollable 모아보기 panel switches between 저장한 글 (default) and 지원금·소식. Below 650px available root width, outer tabs switch between discussion and 모아보기 without unmounting drafts; inner tabs preserve the saved/resource views. The previous sparse profile aside is removed; the header bookmark shortcut opens the right saved panel instead of filtering the discussion feed.
- Right-side saved posts use the existing authenticated `GET /api/owner/community?shopId&savedOnly=true&page` and canonical account-bound bookmark rows. Saving in discussion refreshes the right list; removing a saved item updates the left post flag while keeping that ordinary post in the feed. Saved item selection opens the real discussion detail (and switches to discussion on mobile). Responses are server-confirmed, pagination stays20 per page, and pending reads are aborted on view changes/unmount or before removal. No localStorage, schema change, new saved-post endpoint or duplicated persistence is introduced. Post-editor drafts disable saved-item navigation until saved/cancelled.
- Resources contain `id,title,body,sourceUrl,closesOn,closed,published,createdAt,updatedAt`. Titles are 1-100 characters, body 1-5000, source URL at most 2000. The optional URL must be HTTP(S) without embedded credentials. The server does not fetch it; external links use noopener/noreferrer. Optional deadline is a valid ISO date; closed status uses the current Korean date. Deadlines label a resource but do not delete or automatically hide it. No actual government entitlement, eligibility, application date or automated schedule is inferred.
- GET `/api/owner/community/resources?shopId&page` verifies the existing shop membership, returns only published resources (20 per page, newest/id descending), private/no-store and mobile CORS. `canPublish` is a fail-closed capability from a separately verified active admin session; it is not accepted from owner input. The resource panel loads/fails independently of discussion.
- `/admin/community` now has 소식 관리 and 신고 관리. The existing report flow is preserved. Operators can create, edit, hide and republish resources. GET/POST `/api/admin/community/resources` require the existing active admin session; the SQL RPC repeats the active-admin lookup. JSON writes enforce a streaming 40KB cap, HTTP-origin checks and safe field validation. Origin checks use the browser Host with the request protocol, including when NextURL normalizes loopback IPs to localhost; foreign origins and cross-site metadata remain rejected. Request identity/audit fields are stripped; verified admin ID is server-supplied. Create uses stable UUID idempotency; update/delete requires `expectedUpdatedAt` to prevent lost updates. Hidden resources are visible only to administrators.
- `community_resources` and its three invoker functions have RLS/browser ACL denial/service-only access, plus an index for the published feed. Operator IDs are audit fields and never appear in the member response. Resources persist until operator action; no customer notifications, external scraping, AI responses or background posting are introduced. Canonical migration is `20261111153437_community_resources.sql`; hosted application is a separate authorized step.
