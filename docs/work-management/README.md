# 업무별 Codex 사용 안내

대표는 기존 `petmanager` 프로젝트에서 “관리자 상태를 5단계로 정리해줘”처럼 한두 문장으로 지시하면 됩니다. 주담당이 범위·완료 조건을 정하고 필요한 역할만 부릅니다. 영구 대기 팀이나 별도 앱 칸반을 만들지 않습니다.

## 적용 범위

- 공통 규칙 원본: `D:/petmanager-shared/AGENTS.md`. 기존 `sync-agents.ps1`만으로 PC/app 사본을 동기화합니다.
- 이번 역할 설치: PC `D:/petmanager/.codex/config.toml`과 `.codex/agents/pm-*.toml`. 모바일 `D:/petmanager-app`에는 역할을 설치하지 않았으며 저장소 분리를 유지합니다.
- 현재 운영팀 작업공간은 접수·조정용입니다. 현재 채팅이 PC 프로젝트로 이동하거나 PC 역할을 자동 로딩한 것은 아닙니다.
- 설정은 현재 PC 원본에만 로컬 적용하며 커밋·보호 브랜치 반영은 하지 않았습니다. 새 작업본은 수용된 코드·미커밋 변경과 함께 공통 지침·역할 파일이 실제로 포함됐는지 확인해야 합니다.
- 기존 채팅·AO 작업본은 새 지침을 자동 재주입받았다고 가정하지 않습니다. 실제 PC 프로젝트의 새 작업에서 설정을 읽고 시작합니다. 기존 채팅 생성·이름 변경·보관을 자동 실행하지 않습니다.

## 대표 확인 주소·환경 고정

- PC 관리자/오너 구현 기준 저장소는 오직 `D:\petmanager`입니다. 오래된 검사본·복사본·격리 작업본은 내부 QA에만 쓰고 대표 확인본으로 안내하지 않습니다.
- 대표에게 안내할 PC 로컬 기본 주소는 오직 `http://127.0.0.1:3000`입니다. `localhost`와 다른 포트는 대표 확인 링크로 쓰지 않습니다.
- 오너는 `http://127.0.0.1:3000/owner`, 관리자는 `http://127.0.0.1:3000/admin`입니다. 다른 경로는 현재 `D:\petmanager` 소스의 실제 route를 확인한 뒤만 기록합니다.
- 서버 시작·링크 공유 전 `D:\petmanager`에서 `npm run check:owner-preview`를 실행합니다. 저장소·주소·route·환경·검수용 연습 DB 기준이 하나라도 다르면 시작을 중단하고 다른 링크로 대체하지 않습니다.

| 구분 | 고정 표기 | 설명 |
| --- | --- | --- |
| PC 화면 | `[PC 로컬]` | 대표 PC의 `127.0.0.1:3000` 서버 |
| 외부 확인용 화면 | `[검수 서버]` | 외부 기기에서 확인할 서버 |
| 고객 실사용 화면 | `[운영 서버]` | 대표의 별도 배포 지시 후만 변경 |
| 연습 데이터 | `검수용 연습 DB` | 로컬 서버와 별개인 연습용 데이터 저장소 |
| 고객 데이터 | `고객용 운영 DB` | 실제 고객 데이터 저장소 |

보고할 때는 서버와 DB를 별도로 붙여 `[PC 로컬 + 검수용 연습 DB]`처럼 적습니다. 포트 3000을 DB로 설명하지 않습니다. 커밋·push·배포는 대표가 나중에 `커밋해줘` 또는 `배포해줘`라고 명시한 범위에서만 진행합니다.

## 필요한 역할만 사용

| 역할 | 하는 일 | 쓰기 경계 |
| --- | --- | --- |
| 조사 담당 | 코드·문서 조사와 근거 정리 | 읽기 전용 |
| 화면 설계 담당 | 실제 화면·소스를 보고 설계 도면만 반환 | 읽기 전용, 구현 금지 |
| 구현 담당 | 승인된 범위와 설계 구현 | 한 업무의 유일한 제품 작성자 |
| 기능 검수 담당 | 독립 기능 검수 | 지정 테스트·검증 산출물만 |
| 화면 검수 담당 | 독립 실제 화면 검수 | 지정 캡처·검증 산출물만 |

주담당 외 동시 하위 담당은 최대 3명입니다. 같은 업무 구현자는 독립 검수자가 될 수 없습니다. 모든 역할의 모델·추론·승인 모드는 현재 설정을 상속하며 임의로 바꾸지 않습니다. QA의 `workspace-write`는 파일 권한 상한 안에서 산출물을 만들기 위한 것으로 제품 수정 허용이 아닙니다. 런타임의 상위 권한이 넓더라도 역할 경계를 지킵니다.

UI 작업은 실제 화면/소스 확인 → 설계 도면 → 단일 구현 → 독립 기능·화면 검수 순서입니다. UI playbook은 실제 UI 작업 경계에서 읽습니다. UI가 없는 변경은 필요한 조사·구현·독립 기능 검수만 진행하고, 순수 조사는 조사만으로 끝냅니다.

## 복합 업무를 나누는 기준

[AI 총괄 운영팀 업무 지시서 v0.1](https://app.notion.com/p/3caac017503d817080d4f4184730f7f0?pvs=204)에서 현재 Codex 방식과 맞는 규칙만 적용합니다. 이 문서는 참고 자료이며 공통 지침과 대표의 승인 경계를 대신하지 않습니다.

- 복합 업무는 필요한 깊이까지만 나눕니다. 내부 기록에는 업무 ID, 담당, 완료 조건, 필수 선행 작업, 현재 막힘, 다음 행동을 남깁니다.
- 필수 선행 작업이나 필수 하위 작업이 끝나지 않으면 이에 의존하는 다음 단계와 상위 업무를 완료로 열지 않습니다. 서로 독립적인 작업만 파일 소유권을 나눠 병렬로 진행합니다.
- 담당은 배정된 업무와 파일 범위만 수행합니다. 범위 밖에서 발견한 일은 임의로 구현하지 않고 별도 제안이나 다음 업무 후보로 반환합니다.
- 새 요청으로 전환할 때 기존 업무를 덮어쓰지 않습니다. 완료한 일, 현재 진행, 다음 행동, 확정된 결정, 막힘을 짧은 체크포인트로 남겨 재개 위치를 보존합니다.
- `조치필요`에는 막힌 단계, 원인, 필요한 결정·권한·자료, 영향을 받는 다음 작업, 막힘이 풀린 뒤의 다음 행동을 함께 기록합니다.
- 주담당은 먼저 안전한 읽기·진단·대안 확인으로 해결을 시도합니다. 승인·새 권한·중대한 제품 결정이 필요하면 범위를 넓히지 않고 대표에게 한 번만 질문합니다.
- DB·Auth·결제·삭제·환경변수·도메인·배포처럼 승인이 필요한 작업은 기존 승인 규칙을 유지하고, 실행 전 정확한 대상·영향·복구 방법을 확인합니다.

### 업무 연속성 선택 규칙

- 대표 요청 하나를 상위 `parent_work_id` 하나로 고정합니다. 계획 단계는 같은 ID 아래 `A-1`, `A-2`, `A-3`처럼 만들고 각 단계에 `depends_on`, `lane`, 완료 조건을 기록합니다. 별도 대표 요청 B는 A의 하위 단계가 아닙니다.
- 같은 `lane`에는 `active` 단계가 하나만 있을 수 있습니다. 쓰기 파일이 겹치지 않아도 같은 lane의 두 단계를 동시에 시작하지 않습니다.
- 단계가 끝날 때마다 다음 후보를 다시 계산합니다. `depends_on`이 모두 완료된 단계를 `next-ready`로 보고, 현재 상위 업무의 `next-ready`를 다른 상위 업무보다 먼저 선택합니다. 따라서 `A-1 완료` 뒤 기본 선택은 `A-2`입니다.
- 다른 상위 업무 B는 대표가 우선순위를 명시적으로 바꾸었거나, A와 `lane`·파일 소유권·승인 대기·실행 자원이 실제로 독립적일 때만 병렬로 시작합니다. 이 예외의 근거를 업무 기록에 남깁니다.
- 개별 담당의 `completed`는 그 단계의 산출물 제출 신호일 뿐입니다. 상위 업무는 모든 필수 단계의 완료 조건, 상위 acceptance gate, 필요한 독립 QA가 PASS이고 미해결 P0/P1이 0일 때만 `완료`입니다.
- `interrupted`, `failed`, 또는 마지막 실제 메시지·도구 결과 뒤 10분간 새 출력이 없으면 해당 단계를 `stalled`로 판정합니다. 승인·입력 대기는 `blocked`이며 무출력 정체로 재촉하지 않습니다.
- `stalled`에는 같은 단계·같은 `parent_work_id`로 재개 신호를 한 번만 보냅니다. 다시 `stalled`이면 기존 담당의 쓰기 중지와 소유권 반환을 확인하고 소유권을 회수한 뒤, compact handoff만 전달해 같은 단계 ID의 새 담당으로 교체합니다.
- `blocked` 기록에는 원인, 재개 조건, 영향을 받는 단계, 막힘이 풀리면 선택할 `next-ready`, `owner_approval_required: Y/N`을 반드시 적습니다. Y이면 대표에게 한 번만 요청하고 자동 재시도하지 않습니다.
- 새 역할 파일과 문서는 기존 활성 task에 자동 반영되지 않습니다. 활성 task에는 아래 필수 필드와 선택 규칙만 compact delta로 별도 전달하고, 수신 확인 전 새 규칙을 적용했다고 보지 않습니다.

선택 순서는 `같은 parent의 next-ready` → `명시적으로 우선순위가 바뀐 업무` → `독립 lane의 next-ready`입니다. 어느 후보도 열리지 않으면 새 업무를 임의로 시작하지 않고 blocker와 재개 조건을 보고합니다.

## 기록과 상태

주담당은 [업무 기록 틀](WORK-TEMPLATE.md)을 복사해 한 업무를 관리합니다. 현재 인계 대상은 [현재 업무 인계](CURRENT-HANDOFF.md)에 있습니다. 같은 프로젝트의 다른 채팅이 기억을 자동 공유한다고 가정하지 않습니다.

연속성 규칙은 [검증 시나리오](CONTINUITY-SCENARIOS.md)의 다섯 전이가 모두 유일한 결과를 내야 통과입니다.

- `지시사항`: 요청은 접수했지만 아직 실행을 배정하지 않음.
- `작업중`: 담당과 실제 실행 근거가 있음.
- `조치필요`: 승인·소유권·기준선 등 해결할 조건이 있음.
- `검수필요`: 구현 근거가 제출됐고 독립 검수가 남음.
- `완료`: 미해결 P0/P1이 0건이고 모든 완료 조건과 필요한 독립 검수가 통과함. 검증불가는 통과가 아님.

고정 시간 재지시와 반복 상태 조회는 하지 않습니다. 완료·입력 필요 이벤트를 기다리며, 승인 대기는 한 번 알리고 멈춥니다. 요청된 감시도 목적이 끝나거나 더 확인할 이유가 없어지면 중지합니다. Notion은 대표가 정한 승인 기록·관련 문서가 필요한 경우에만 한 번 조회하고, 명시적 요청 또는 이미 승인된 기록 범위에서만 외부 갱신합니다.

각 담당은 긴 대화가 되기 전에 목적·결정·변경 파일·검증·막힘·다음 단계만 인계합니다. 도구 40회/큰 읽기 12회/실제 작업 45분 전에 새 담당으로 넘기고, 기존 작성자의 중지·소유권 반환과 새 담당의 기준선 확인을 먼저 합니다. 새 담당이 불가능하면 인계 후 새 작업에서 재개하도록 요청합니다.

제품 소스 수정·운영 배포는 이 설정 전환의 결과가 아닙니다. 운영 배포·보호 브랜치 갱신·원격 DB/Auth·실결제·외부 발송·비용 발생은 명시적 최종 승인을 별도로 받습니다. 작업 소유 서버·자동 브라우저는 완료/인계 전에 종료 확인하며 개인 브라우저와 유지 요청된 3000 서버는 보존합니다.

설정 형식·상속·읽기 시점은 [공식 서브에이전트 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents)와 [AGENTS.md 문서](https://learn.chatgpt.com/docs/agent-configuration/agents-md)를 기준으로 확인했습니다. 이 안내는 계정의 실제 실행 권한을 확대하지 않습니다.
